# برنامه آزمون بتای ۱۰ نفره پاتوق V14

## هدف و محدودیت

این برنامه برای آزمون واقعی روی **Staging** است. موفقیت تحلیل ایستا یا ساخت APK به‌تنهایی تأیید کارکرد چندکاربره، امنیت نقش‌ها یا آمادگی انتشار نیست. در این آزمون از داده ساختگی قابل‌شناسایی و حساب‌های آزمایشی استفاده شود؛ هیچ داده واقعی حساس یا کلید Production وارد نشود.

## آماده‌سازی قبل از دعوت

- [ ] از دیتابیس Staging پشتیبان تهیه شده و شناسه پروژه با `sxglkafhprigkeqdtanr` تطبیق داده شده است.
- [ ] وضعیت پروژه Healthy است و دامنه Staging از شبکه گوشی‌ها قابل دسترسی است.
- [ ] Migrationها در ترتیب درست و فقط روی Staging اعمال شده‌اند؛ تاریخچه migration قبل و بعد ذخیره شده است.
- [ ] RLS و مجوز RPCها با حساب مجاز، کاربر عادی و نشست بدون احراز بررسی شده‌اند.
- [ ] APK هر ده گوشی از یک Run و یک Commit ساخته شده؛ version/build number و SHA-256 ثبت شده است.
- [ ] هر آزمایشگر شناسه/شماره آزمایشی یکتا دارد؛ یک نشست Anonymous مشترک روی چند گوشی استفاده نمی‌شود.
- [ ] حساب ادمین از قبل با مجوز سمت سرور تعیین شده؛ کاربر عادی نمی‌تواند خودش نقش ادمین انتخاب کند.

## تقسیم نقش پیشنهادی

| آزمایشگر | نقش اصلی آزمون | هدف |
|---|---|---|
| T01 | ادمین مجاز | بررسی درخواست نقش‌ها و پنل ادمین |
| T02 | میزبان | مکان، ظرفیت، مشاهده رزروهای مجاز |
| T03 | هماهنگ‌کننده | عملیات مجاز روی رویدادهای تحت مسئولیت |
| T04 | برگزارکننده | ایجاد/ویرایش رویداد در محدوده مجاز |
| T05–T10 | شرکت‌کننده | ثبت‌نام، علایق، پیشنهادها، رزرو، پست، کامنت و عضویت |

اگر نقش حرفه‌ای هنوز توسط ادمین/سرویس مجاز نشده، آن را با تغییر محلی فعال نکن؛ نتیجه را به‌عنوان «مجوز نقش آماده نیست» ثبت کن.

## سناریوهای آزمون

### A. ثبت‌نام و پروفایل

- [ ] هر نفر با حساب یکتا وارد Staging شود.
- [ ] حساب جدید حداقل سه علاقه انتخاب کند و بدون تکمیل حداقل‌ها نتواند ادامه دهد.
- [ ] پرسش‌نامه ۸ سؤالی کامل شود و پاسخ‌ها ذخیره شوند.
- [ ] فیلدهای اختیاری خالی بمانند و فرم همچنان قابل تکمیل باشد.
- [ ] پس از بستن و بازکردن برنامه، علایق و پاسخ‌های ذخیره‌شده برگردند.
- [ ] کاربر نتواند پروفایل محلی یک کاربر دیگر را ببیند یا جایگزین کند.

### B. خانه و دسته‌ها

- [ ] بنرهای تبلیغاتی باقی باشند.
- [ ] خانه شبکه ۱۲ دسته داشته باشد و بخش کارت‌های رویداد/پیشنهاد قدیمی در آن دیده نشود.
- [ ] لمس هر دسته، رویدادهای همان دسته را نشان دهد؛ دسته خالی پیام واضح داشته باشد.
- [ ] هدر راست‌به‌چپ: پروفایل سمت راست، لوگوی پاتوق وسط، اعلان‌ها سمت چپ.
- [ ] راهنمای سراسری از هر صفحه قابل دسترسی باشد.

### C. داده مشترک و رزرو

- [ ] برگزارکننده یک رویداد آزمایشی منتشر کند؛ شرکت‌کننده مجاز آن را بدون نصب مجدد ببیند.
- [ ] دو شرکت‌کننده برای ظرفیت محدود هم‌زمان رزرو کنند؛ ظرفیت و نتیجه نهایی در سرور درست بماند.
- [ ] رزرو و لغو رزرو فقط در محدوده مجوزها انجام شود.
- [ ] میزبان/هماهنگ‌کننده فقط داده‌های مربوط به محدوده دسترسی خود را ببیند.
- [ ] کاربر عادی نتواند با درخواست مستقیم، رویداد یا رزرو دیگران را دستکاری کند.

### D. تایم‌لاین و رسانه

- [ ] کاربر مجاز یک پست متنی و یک پست رسانه‌ای منتشر کند.
- [ ] کاربران دیگر پست را ببینند؛ لایک و لغو لایک شمارنده صحیح داشته باشد.
- [ ] کامنت، ذخیره و اشتراک‌گذاری به سرور متصل و پس از ورود مجدد قابل مشاهده باشند.
- [ ] کاربر بلاک‌شده یا بدون مجوز نتواند عملیات ممنوع انجام دهد.
- [ ] فایل رسانه‌ای نامعتبر/بزرگ و خطای شبکه پیام قابل‌فهم بدهند.

### E. چت، گروه، کانال و استوری

- [ ] ارسال و دریافت پیام از دو حساب آزمایشی بررسی شود.
- [ ] عضویت/ترک گروه و محدودیت انتشار کانال با نقش مناسب آزمایش شود.
- [ ] اعلان و استوری از حساب دیگر فقط در محدوده دسترسی دیده شوند.
- [ ] هر قابلیتی که هنوز سروری نشده، صریحاً به‌عنوان محدودیت ثبت شود؛ ظاهر دکمه، موفقیت محسوب نمی‌شود.

### F. بازی‌ها

- [ ] ساخت اتاق و عضویت/ترک آن از دو گوشی مختلف روی Staging ثبت شود.
- [ ] کد اتاق، ظرفیت و وضعیت اتاق در هر دو گوشی سازگار باشد.
- [ ] دوز: دو کاربر به نوبت حرکت کنند؛ حرکت خارج از نوبت، خانه اشغال‌شده، برد و مساوی از سمت سرور بررسی شوند.
- [ ] مار و پله: تاس از سمت سرور تولید شود؛ جایگاه و نوبت هر دو/چند کاربر روی دستگاه دیگر به‌روز شود و رسیدن به خانه ۱۰۰ برنده را تعیین کند.
- [ ] شطرنج و تخته‌نرد تا پیاده‌سازی و تست موتور قوانین، Blocked محسوب شوند و به‌عنوان بازی کامل معرفی نشوند.
- [ ] **Migration وضعیت بازی هنوز باید روی Staging اجرا و بررسی شود؛ ساخت اتاق به‌تنهایی تست بازی محسوب نمی‌شود.**

### G. پنل نقش‌ها و امنیت

- [ ] نقش‌های participant، venue، coordinator، organizer و admin جداگانه آزمون شوند.
- [ ] کاربر عادی نتواند با دست‌کاری UI/درخواست API نقش یا رکورد مدیریتی بگیرد.
- [ ] کاربران بلاک‌شده، نشست منقضی و کاربر ناشناس در هر RPC حساس آزمایش شوند.
- [ ] گزارش/خطا شامل کلید یا توکن محرمانه نباشد.

## ثبت نتیجه هر سناریو

برای هر مورد ثبت شود: شناسه سناریو، حساب/نقش، دستگاه، زمان، Commit APK، نتیجه (Pass/Fail/Blocked)، پیام خطا و تصویر. هیچ خطای Blocked به‌عنوان Pass گزارش نشود.

## شرط پذیرش بتا

بتا فقط وقتی «آماده» اعلام شود که مسیرهای اصلی A–D و نقش‌ها روی سرور Staging موفق باشند، هیچ شکست امنیتی بحرانی باقی نمانده باشد و تمام قابلیت‌های ناقص—به‌خصوص موتور بازی—به‌روشنی از دامنه تست واقعی جدا شده باشند.

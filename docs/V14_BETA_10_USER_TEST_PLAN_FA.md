# برنامه تست بتای ۱۰ نفره پاتوق V14

این سند برای محیط **Staging** است. در این مرحله هیچ Migration یا تست نوشتنی روی Production اجرا نشود.

## ۱) تقسیم نقش‌ها

- کاربر ۱: ادمین آزمایشی؛ بررسی درخواست نقش‌ها، گزارش‌ها و مدیریت دسته‌ها.
- کاربر ۲: برگزارکننده؛ ساخت/مدیریت رویداد طبق مجوز سرور.
- کاربر ۳: هماهنگ‌کننده؛ بررسی عملیات مجاز هماهنگی.
- کاربر ۴: میزبان؛ مشاهده داشبورد میزبان و رویدادهای متعلق به خود.
- کاربران ۵ تا ۱۰: شرکت‌کننده؛ ثبت‌نام، علایق، پیشنهادها، رزرو، تایم‌لاین و اجتماع.

نقش حرفه‌ای نباید صرفاً با انتخاب در UI فعال شود؛ درخواست باید از مسیر role request تأیید شود و سرور مجوز نهایی را اعمال کند.

## ۲) پیش‌نیازهای محیط

1. تمام ۱۰ نصب از همان `STAGING_SUPABASE_URL` و `STAGING_SUPABASE_ANON_KEY` استفاده کنند.
2. تأیید شود URL به پروژه `sxglkafhprigkeqdtanr` اشاره می‌کند؛ URL پروژه Production `dzbslxoquiwgabdtwjbv` است و نباید در این تست تغییر کند.
3. پروژه Staging باید از حالت Paused خارج و Healthy باشد.
4. Migrationهای موردنیاز باید فقط روی Staging اجرا شوند. حداقل migration موجود `20261003160000_v14_timeline_social.sql` و migration پروفایل V14 با نام `20261020130000_v14_profile_personality.sql` هستند.
5. قبل از اجرای migration، backup یا راه بازیابی Staging تأیید شود. Migrationها را روی Production اجرا نکنید.
6. Realtime برای جدول‌های لازم در publication `supabase_realtime` فعال باشد.

## ۳) سناریوهای پذیرش

### ثبت‌نام و پروفایل
- [ ] کاربر جدید حداقل ۳ علاقه انتخاب می‌کند.
- [ ] هر ۸ سؤال ترجیحات اجتماعی پاسخ داده می‌شود و پاسخ‌ها ذخیره می‌شوند.
- [ ] تحصیلات، تأهل، فرزند و سربازی اختیاری‌اند.
- [ ] بستن و بازکردن برنامه اطلاعات را پاک نمی‌کند.
- [ ] ورود مجدد، همان پروفایل و علایق را برمی‌گرداند.
- [ ] اطلاعات حساس مانند تلفن یا پاسخ‌های اختیاری کاربران دیگر در پیشنهادها افشا نمی‌شود.

### پیشنهاد هم‌پاتوقی
- [ ] پیشنهادها از پروفایل‌های واقعی تکمیل‌شده Staging می‌آیند، نه کاربران ساختگی.
- [ ] کاربر خودش در نتایج نیست.
- [ ] بلاک دوطرفه، نمایش کاربر را محدود می‌کند.
- [ ] سن فقط وقتی `show_age=true` است برگردانده می‌شود.
- [ ] پیشنهادها با علایق/تگ‌های مشترک و شهر مرتب می‌شوند؛ درصد علمی ساختگی نمایش داده نمی‌شود.

### رویداد و رزرو
- [ ] رویداد تازه از دستگاه برگزارکننده در دستگاه‌های مجاز دیگر ظاهر می‌شود.
- [ ] دو شرکت‌کننده برای ظرفیت آخر هم‌زمان تلاش می‌کنند؛ سرور از رزرو بیش از ظرفیت جلوگیری می‌کند.
- [ ] رزرو، لغو و وضعیت انتظار پس از refresh و ورود مجدد درست است.
- [ ] شرکت‌کننده نمی‌تواند عملیات مختص برگزارکننده/ادمین را از API انجام دهد.

### تایم‌لاین و اجتماع
- [ ] پست و رسانه از یک کاربر به دیگران نمایش داده می‌شود.
- [ ] لایک/لغو لایک، کامنت، ذخیره و Share بین دستگاه‌ها با داده سرور هم‌خوان است.
- [ ] گزارش و بلاک حفظ شده و روی نمایش محتوا اعمال می‌شوند.
- [ ] ساخت گروه/کانال و عضویت از چند دستگاه بررسی می‌شود.
- [ ] پیام متنی و رسانه در دو دستگاه دریافت می‌شود و بعد از قطع‌وصل تکراری یا گم‌شده نیست.

### بازی‌ها
- [ ] ساخت، فهرست و عضویت اتاق از RPCهای Staging روی دو دستگاه انجام می‌شود.
- [ ] اتاق‌های ساختگی و شمارنده ثابت بازیکن آنلاین نمایش داده نمی‌شوند.
- [ ] اتاق فقط وقتی «بازی آنلاین کامل» محسوب می‌شود که موتور قوانین، نوبت‌ها و وضعیت همگام‌شده هم واقعاً کار کند. (این بخش هنوز پیاده‌سازی نشده است.)
- [ ] دو دستگاه وضعیت بازی یکسان و ترتیب نوبت را می‌بینند؛ این تست تا تکمیل موتور بازی مسدود است.
- [ ] قطع و وصل شبکه، خروج بازیکن و دعوت دوباره آزمایش می‌شود.
- [ ] اگر هر بازی هنوز محلی/نمایشی است، در رابط به‌عنوان آنلاین واقعی معرفی نشود.

### پنل نقش‌ها و راهنما
- [ ] هر نقش فقط داده و عملیات مجاز خود را می‌بیند.
- [ ] آمار پنل‌ها از سرور می‌آید و از شمارنده ثابت/Mock استفاده نمی‌کند.
- [ ] دکمه راهنما در تمام صفحات قابل دسترسی است و متن آن ادعای قابلیت پیاده‌نشده نمی‌کند.

## ۴) معیار پایان بتا
